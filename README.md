# Домашнее задание к занятию «Базы данных, их типы» — Степанов Андрей

## Задание 1. СУБД

### 1.1. Бюджетирование, финансовые отчёты и прогнозирование рисков

Я выбрал бы **реляционную СУБД PostgreSQL**. Проекты, статьи бюджета, договоры и платежи имеют чёткую структуру и связи. Первичные и внешние ключи, ограничения `NOT NULL`, `UNIQUE`, `CHECK` позволяют контролировать корректность данных. Транзакции с подходящим уровнем изоляции обеспечивают согласованное изменение связанных записей.

Например, платёж должен относиться к существующему договору и проекту, а изменение бюджета и запись основания изменения должны фиксироваться вместе. Денежные суммы следует хранить в точном типе `numeric`, а не в типах с плавающей точкой.

SQL подходит для формирования отчётов: можно объединять таблицы, группировать расходы по проектам и периодам, сравнивать план и факт. Прогнозирование рисков выполняется аналитическими алгоритмами на подготовленных данных; сама СУБД не заменяет модель прогнозирования. При росте аналитической нагрузки можно выделить отдельное хранилище, чтобы тяжёлые отчёты не мешали учёту платежей.

### 1.1.* Ускорение хеширования

Для массового вычисления независимых хешей можно использовать **OpenCL API**: он позволяет распараллелить вычисления на CPU и GPU. Альтернатива для GPU NVIDIA — CUDA.

Ускорение имеет смысл, когда объём вычислений компенсирует затраты на передачу данных и запуск вычислительных ядер. Сначала необходимо установить причину задержки. OpenCL не ускоряет автоматически хеш-индексы или SQL-запросы: вычисление нужно реализовать с использованием этого API. Если речь о хранении паролей, нельзя уменьшать стойкость алгоритма ради скорости: намеренная вычислительная сложность защищает от перебора.

Основание: [описание OpenCL от Khronos](https://www.khronos.org/opencl/).

### 1.2. Лендинги и CRM

Для данных лендингов подходит **документоориентированная СУБД**, например MongoDB. У разных проектов могут отличаться наборы блоков, параметры объектов и поля заявок. Документы позволяют хранить такие структуры без изменения общей схемы таблиц для каждого нового поля. Для поиска нужны индексы по реально используемым полям, например идентификатору проекта и времени создания заявки.

Для CRM я выбрал бы **PostgreSQL**. Клиенты, лиды, менеджеры, сделки и история статусов связаны между собой. Реляционная модель помогает исключать дубликаты, поддерживать целостность связей и строить отчёты по воронке продаж. Дополнительные поля можно хранить в `jsonb`, сохраняя обязательные реквизиты в обычных колонках.

Гибкость и скорость определяются также индексами, запросами и архитектурой приложения. Само наличие лендинга не требует отдельной базы: статическая страница может отправлять заявки напрямую в backend CRM.

### 1.2.* Одна СУБД для лендингов и CRM

Да, можно использовать **PostgreSQL с сочетанием реляционных таблиц и `jsonb`**. В таблицах хранить проекты, контакты, лиды, сделки и ответственных менеджеров; в `jsonb` — конфигурацию лендинга и дополнительные поля формы.

Например, таблица `leads` содержит обязательные поля `id`, `project_id`, `created_at`, `status` и колонку `extra_fields jsonb`. Связь с проектом контролируется внешним ключом. Для часто используемых JSON-полей можно создать индексы под конкретные запросы. Создание лида и начальной записи его истории выполняется одной транзакцией.

Это даёт единое хранилище без обязательной синхронизации двух СУБД. Возможности JSON описаны в [документации PostgreSQL](https://www.postgresql.org/docs/current/datatype-json.html).

### 1.3. Корпоративные нормы, правила и обучающие материалы

По структуре данных подходит **иерархическая модель**: компания → департамент → отдел → раздел → документ. Она понятна пользователям и удобна для навигации по дереву материалов.

Для реализации я выбрал бы PostgreSQL, представив иерархию таблицами. Отдельная специализированная иерархическая СУБД для этого не обязательна. У материала должны быть название, владелец, версия, статус актуальности и права доступа. Если один документ относится к нескольким подразделениям, связь следует хранить отдельно, чтобы не дублировать документ.

### 1.3.* Использование ранее выбранной СУБД

Можно использовать PostgreSQL из предыдущих задач, выделив отдельную схему базы и роли доступа. Например:

- `departments(id, parent_id, name)` — дерево подразделений;
- `sections(id, parent_id, name)` — дерево разделов;
- `documents(id, section_id, title, version, content)` — материалы;
- `document_departments(document_id, department_id)` — принадлежность документа нескольким подразделениям.

Поле `parent_id` ссылается на родителя в той же таблице. Для получения ветви дерева используются рекурсивные запросы `WITH RECURSIVE`. Необходимо отдельно предотвращать циклы в иерархии, поскольку внешний ключ сам по себе их не исключает. Большие файлы можно хранить в объектном хранилище, оставляя в базе метаданные и ссылки.

Основание: [рекурсивные запросы PostgreSQL](https://www.postgresql.org/docs/current/queries-with.html).

### 1.4. Маршруты доставки и распределение курьеров

Подходит **графовая СУБД**, например Neo4j. Объекты, склады и точки доставки представляются вершинами, а дороги и допустимые перемещения — рёбрами. У рёбер можно хранить расстояние, время проезда, стоимость и ограничения. Такая модель удобна для обхода связей и поиска путей.

При построении маршрута учитывать нужно не только расстояние, но и время, доступность дорог и ограничения транспорта. Для распределения нескольких курьеров с учётом вместимости, рабочего времени и временных окон потребуется алгоритм решения задачи маршрутизации транспорта. Графовая СУБД хранит сеть и помогает получать исходные данные, а оптимизацию назначений выполняет соответствующий алгоритм или отдельный сервис. Пример поиска пути — [алгоритм Дейкстры в Neo4j Graph Data Science](https://neo4j.com/docs/graph-data-science/current/algorithms/dijkstra-source-target/).

### 1.4.* Подключение отдела закупок

Отдел закупок можно подключить к общему графу для анализа связей «поставщик → материал → склад → объект» и планирования поставок. При этом права доступа должны соответствовать задачам отдела.

Для учёта заказов, договоров, цен и платежей я оставил бы реляционную PostgreSQL. В граф передавал бы необходимые логистические данные по устойчивым идентификаторам через события или периодическую синхронизацию. Для каждой сущности нужно определить основную систему хранения и правила обработки задержек обновления. Так финансовый учёт и маршрутизация получают подходящие модели без независимого изменения одних и тех же данных в двух местах.

### 1.5.* Одна СУБД для всех задач

Да, при умеренной нагрузке все перечисленные задачи можно реализовать на **PostgreSQL**:

- бюджетирование и CRM — реляционные таблицы и транзакции;
- переменные данные лендингов — `jsonb`;
- база знаний — таблицы с иерархией и рекурсивные запросы;
- логистика — таблицы вершин и рёбер, а для географических данных и маршрутов — расширения PostGIS и pgRouting.

Здесь используется одна базовая СУБД с расширениями, а не только её встроенные возможности. Планирование курьеров и прогнозирование рисков по-прежнему требуют прикладных алгоритмов. Выбор единой СУБД упрощает сопровождение, но при больших объёмах графовых обходов или аналитики специализированные решения могут быть эффективнее. Окончательный выбор следует проверить на типовых запросах и ожидаемых объёмах данных.

## Задание 2. Транзакции

### 2.1. Пополнение баланса телефона: шесть действий

1. **Создать платёж.** Пользователь указывает номер телефона, сумму и источник средств, затем подтверждает операцию. Система проверяет реквизиты и присваивает платежу уникальный идентификатор для защиты от повторного выполнения.
2. **Проверить возможность списания.** Банк или платёжная система проверяет доступный остаток, лимиты и разрешение на операцию. При недостатке средств платёж отклоняется.
3. **Зафиксировать списание.** В локальной транзакции банка списываются средства и создаётся запись о платеже. Проверка остатка и изменение баланса защищаются от конкурирующих списаний. При ошибке этой локальной транзакции выполняется откат.
4. **Передать запрос оператору.** Платёжная система отправляет номер, сумму и идентификатор операции. Запрос должен быть надёжно сохранён для повторной доставки при техническом сбое.
5. **Зачислить средства.** Оператор проверяет запрос и в своей локальной транзакции увеличивает баланс телефона и фиксирует платёж. Повторный запрос с тем же идентификатором возвращает прежний результат, не зачисляя деньги ещё раз.
6. **Подтвердить результат.** После подтверждения зачисления платёжная система сохраняет окончательный успешный статус и уведомляет пользователя. Успех означает, что списание и зачисление подтверждены.

Банковская система и система оператора обычно не находятся в одной транзакции базы данных. Поэтому сбой после списания нельзя устранить обычным `ROLLBACK` в банке. Если ответ оператора потерян, нужно проверить статус и при необходимости повторить запрос с тем же идентификатором. Если оператор окончательно отклонил зачисление, выполняется отдельная компенсирующая операция возврата. До выяснения результата платёж остаётся в промежуточном статусе.

Для локальных транзакций важны свойства ACID: атомарность изменений, соблюдение ограничений целостности, изоляция параллельных операций и сохранность зафиксированного результата.

### 2.1.* Автоплатёж

При автоплатеже пользователь заранее задаёт правило: порог баланса или расписание, номер телефона, сумму, источник средств и лимиты, а также разрешает автоматическое списание.

Далее процесс состоит из тех же шести действий. Разница в запуске: на первом шаге платёж создаёт сервис по событию снижения баланса или по расписанию. Перед созданием он проверяет, что правило активно, лимит не превышен и для данного события ещё нет выполняемого или успешного платежа.

Банк проверяет действующее разрешение на автосписание. Каждому запуску назначается уникальный идентификатор, чтобы повторная обработка события не вызвала второе списание. При недостатке средств пользователь получает уведомление; повторные попытки выполняются по правилам сервиса. При неопределённом результате сначала проверяется существующая операция, а не создаётся новый платёж.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL-систем

Под SQL-системами здесь понимаются традиционные реляционные СУБД. Сравнение относится к типичным возможностям моделей, поскольку конкретные NoSQL-системы тоже могут поддерживать транзакции и проверку схемы.

1. **Контроль целостности связанных данных.** Первичные и внешние ключи, уникальность и проверочные ограничения позволяют задавать правила непосредственно в базе, например запрещать платёж по несуществующему договору.
2. **Транзакции над несколькими таблицами.** Изменения заказа, его позиций и остатков можно фиксировать атомарно, выбирая необходимый уровень изоляции. Это удобно для бизнес-процессов с несколькими связанными сущностями.
3. **Сложные запросы средствами SQL.** Соединения, подзапросы, группировки и оконные функции позволяют строить отчёты без предварительного переноса всех вычислений в приложение.
4. **Нормализация и снижение дублирования.** Общие сведения можно хранить в одном месте и связывать по ключам. Например, изменение реквизитов поставщика не требует исправлять их копии во всех заказах.
5. **Стандартизованный язык и развитая экосистема.** SQL широко поддерживается инструментами аналитики, драйверами и средствами администрирования. Это облегчает обучение и интеграцию, хотя диалекты и возможности разных СУБД отличаются.

Эти преимущества не означают, что SQL всегда быстрее NoSQL: производительность зависит от модели данных, запросов, индексов и нагрузки.

### 3.1.* Преимущества NewSQL

**NewSQL** сочетает реляционную модель, SQL и транзакционные гарантии с архитектурой для горизонтального масштабирования. Примеры — CockroachDB и TiDB.

По сравнению с традиционной архитектурой с одним пишущим сервером такие системы могут распределять данные и обработку транзакций между узлами, поддерживать автоматическое перераспределение данных и отказоустойчивость. По сравнению с NoSQL-системами, ориентированными на ослабленную согласованность, они позволяют сохранять реляционную модель и строгие гарантии транзакций без переноса всей логики согласования в приложение.

Это особенно полезно для растущей транзакционной системы, которой уже тесно на одном сервере. Однако распределённые транзакции требуют сетевого взаимодействия и координации: увеличиваются задержки и сложность эксплуатации. При сетевом разделении сохранение строгой согласованности может ограничить доступность операций. NewSQL не гарантирует преимущество для любого запроса и не заменяет специализированную аналитику.

Пример архитектуры: [официальная документация CockroachDB](https://docs.cockroachlabs.com/docs/stable/architecture/overview).

## Задание 4. Кластеры

**Главный критерий — характер нагрузки и возможность разделить данные и вычисления между узлами.** Само наличие 1000 машин ещё не определяет тип СУБД. Нужно оценить объём данных, виды запросов, долю чтения и записи, допустимое время ответа, требования к согласованности, объём сетевого обмена и устойчивость к отказам.

Если подразумевается пакетная обработка большого массива данных, я выбрал бы **модель MapReduce** и распределённое хранилище. В качестве примера реализации — Hadoop MapReduce с HDFS. HDFS является файловой системой, а MapReduce — моделью и механизмом вычислений; сами по себе они не являются СУБД.

Вычисления выполняются следующим образом:

1. **Разбиение данных.** Исходный набор делится на части, размещённые на узлах кластера с репликацией.
2. **Map.** Узлы параллельно обрабатывают свои части и формируют промежуточные пары «ключ — значение».
3. **Shuffle.** Промежуточные данные группируются и передаются по ключам узлам следующего этапа.
4. **Reduce.** Узлы независимо агрегируют группы и записывают результат.

Например, при подсчёте затрат по строительным объектам Map выдаёт пары `(объект, сумма)`, Shuffle собирает записи одного объекта, а Reduce рассчитывает итоговые расходы.

Модель подходит для 1000 машин, потому что независимые задачи обрабатываются параллельно, вычисления можно приближать к месту хранения данных, а неуспешные задачи — запускать повторно. При этом масштабирование ограничивают перекос распределения ключей, сетевой обмен и последовательные участки алгоритма. Ускорение в 1000 раз заранее гарантировать нельзя.

Если нужен именно слой СУБД для аналитических SQL-запросов, я рассматривал бы распределённую колоночную СУБД с **MPP-архитектурой**, где узлы параллельно сканируют и агрегируют свои части таблиц. Для итерационных алгоритмов полезнее может оказаться Apache Spark, уменьшающий повторное чтение промежуточных данных с диска. Следовательно, для предполагаемой пакетной задачи ответ — MapReduce; для интерактивной SQL-аналитики выбор следует уточнить в пользу MPP.

Основание: [официальное руководство Apache Hadoop MapReduce](https://hadoop.apache.org/docs/stable/hadoop-mapreduce-client/hadoop-mapreduce-client-core/MapReduceTutorial.html), [руководство Apache Spark](https://spark.apache.org/docs/latest/rdd-programming-guide.html).
